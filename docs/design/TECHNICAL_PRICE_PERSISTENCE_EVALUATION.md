# 技術分析歷史價格持久化架構評估

## 1. 問題意識與系統約束

在股票研究工作區（Research Workspace）中，使用者期望能直觀查閱個股近期的歷史價格走勢與技術型態位置。然而，在以 Git 為狀態底層存儲（`research-state` 分支）之架構中，直接保存完整的歷史逐日（或分鐘級）OHLCV 價格序列會面臨重大工程挑戰：

1. **快照體積限制（`MAX_SNAPSHOT_BYTES = 20,000`）**：
   單一研究快照（snapshot JSON）大小上限為 20KB。若存入數年完整 OHLCV 價格序列，快照將迅速突破限制。
2. **Git 倉庫歷史膨脹風險（Repository Bloat）**：
   每日排程對 10 檔（乃至未來更多）標的寫入包含完整價格序列的新版本 JSON，會使 `.git` 目錄以等比級數膨脹，導致 clone / fetch 耗時與 CI 負擔劇增。
3. **不可造假原則（Zero Mock Data）**：
   系統嚴禁假造示意走勢圖；未持久化真實價格即誠實標記為未保存，絕不生成隨機或偽造的走勢圖形。

為了在「滿足技術分析視覺化」與「維持輕量可重播的 Git 狀態儲存」之間取得最佳平衡，評估以下兩種持久化架構方案。

---

## 2. 方案架構對比

### 方案 A：快照內嵌輕量化近期價格陣列（Embedded Recent Closes）

- **設計**：
  在快照的 `technical` 區塊中新增固定長度之近期收盤價陣列（例如最近 30 至 60 個交易日的官方未還原收盤價與交易日）。
  ```json
  "technical": {
    "status": "available",
    "session": "2026-10-19",
    "recent_closes": [
      {"d": "2026-09-01", "c": 940.0},
      {"d": "2026-09-02", "c": 945.0},
      ...,
      {"d": "2026-10-19", "c": 1085.0}
    ]
  }
  ```
- **空間預算分析**：
  - 30 個交易日 × ~25 bytes ≈ 750 bytes（即便 60 個交易日也僅約 1.5 KB）。
  - TSMC 目前完整快照體積約 12 KB，加入後約 12.8 KB，依然充裕低於 `20 KB` 上限。
  - 年增加量（10 檔 × 250 天 × 750B）≈ 1.8 MB / 年，對 Git 儲存庫完全無感知負擔。
- **優勢**：
  - **零外掛依賴**：完全內嵌於快照與 `index.html` 內的 `site-data`。
  - **完全離線可用**：靜態 HTML 下載後在無網路環境下亦能直接繪製近 30–60 天走勢 SVG 折線圖與近期高低點支撐壓力線。
  - **嚴格維持狀態一致性**：價格序列與財務數據、估值情境在同一個快照 Commit 中原子對帳。
- **限制**：
  - 無法呈現多年期長週期趨勢（如 3 年週線圖）。
  - 無法提供完整的開高低收（OHLC）K 線實體與成交量柱狀圖。

---

### 方案 B：工作流產物 Sidecar 契約（Workflow Artifact Sidecar `prices.json`）

- **設計**：
  在每日研究與掃描工作流執行時，將 1 年至 5 年之完整日 K（OHLCV + 成交量）序列輸出為獨立檔案 `prices/{symbol}.json`，存放於 GitHub Actions Artifacts。在 GitHub Pages 發布工作流中，將該目錄一同複製部署至靜態網站根目錄：
  ```
  https://iceboxi.github.io/market-research/prices/2330.TW.json
  ```
  前端頁面於使用者切換至「技術分析」分頁時，透過非同步 `fetch("./prices/2330.TW.json")` 動態加載並以 Canvas / SVG 渲染互動式 K 線圖。
- **空間預算分析**：
  - 1 檔股票 2 年日 K 數據約 500 行，JSON 體積約 25 KB。
  - 10 檔股票合計約 250 KB。
  - **完全不寫入 `research-state` Git 分支**，對 Git 歷史體積膨脹為 0。
- **優勢**：
  - **支援專業級 K 線互動**：可支援完整 OHLCV、成交量、均線（MA20/MA60）與 ATR 指標回測。
  - **狀態分支零負擔**：Git 分支專注於核心研究指標、對帳紀錄與快照 metadata。
- **限制**：
  - 依賴前端非同步網路請求（需考慮網路失敗或延遲之載入狀態與 fallback）。
  - 若歷史 Artifact 過期或清理，靜態網頁端可能出現 404，需具備無檔案時之優雅降級介面。

---

## 3. 綜合評估指標矩陣

| 評估維度 | 方案 A：內嵌輕量收盤陣列 | 方案 B：Sidecar 外部產物 |
| :--- | :--- | :--- |
| **Git 歷史體積衝擊** | 輕微（約 1.8 MB / 年） | **無（0 MB）** |
| **快照 20KB 限制相容性** | **完全符合**（佔用約 0.7–1.5 KB） | 不佔用快照空間 |
| **圖表呈現深度** | 基礎（30–60 日收盤趨勢折線圖） | **完整（1–2 年日 K 線、成交量、均線）** |
| **離線與自包含性** | **極高（單一 HTML 即完整呈現）** | 依賴靜態資源伺服與非同步 fetch |
| **實作複雜度** | **低（擴充快照 schema 與 SVG 產生器）** | 中（需整合 Pages 部署路徑與前端載入狀態） |
| **歷史一致性與重播** | **強（與快照歷史版本嚴格綁定）** | 較弱（Sidecar 檔案通常僅保存最新版） |

---

## 4. 決策結論與分階段實施建議

1. **短期實施（Vertical Slice 優先）**：
   採 **方案 A（輕量化契約）**。
   - 在 `snapshot["technical"]` 新增 `recent_closes: list[dict]`（30 個交易日未還原收盤價）。
   - 在研究工作區技術分析區塊中繪製 30 日輕量走勢折線圖，並標註前 20 日與 60 日支撐壓力位。
   - 效益：以極低代價解除「無價格走勢圖」的體驗缺陷，且單一 HTML 保持自包含與確定性。

2. **長期演進（進階技術分析）**：
   引入 **方案 B 作為漸進增強（Progressive Enhancement）**。
   - 預設優先使用方案 A 之內嵌數據渲染輕量走勢；
   - 若使用者點擊「展開完整歷史 K 線與量能」，則觸發 fetch 載入 Sidecar `prices/{symbol}.json`，無縫切換為高階互動圖表。
